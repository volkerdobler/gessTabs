# Feature Roadmap — Editor Support Extensions

Forward-looking feature proposals (not code-quality cleanup, unlike P0–P3 above), derived from a research pass over `dokumentation/gesstabs_handbuch_52.md` (the ~19,000-line main handbook) and the ~15 topic-specific manuals in the same folder (Makros, CSV-Infile, InvertierteDateien, GESStabs-Artist, OfficeExport, Cellset, HTMLChart, Mehrebenenanalyse, Gewichten, SpaltenweiseSignifikanztests, Scoretab, Basiswechsel, Titlepage-Chapterpage, Totalcolumntable, Encoding). Goal: prioritize tooling that addresses complexity/pitfalls the manuals *themselves* call out as error-prone, rather than generic "nice to have" editor features. Grouped into tiers (F0–F5) by dependency order and value; implement roughly top to bottom, but each item is independently shippable. Line references below are to `dokumentation/gesstabs_handbuch_52.md` unless another file is named.

## F0 — Foundation: correct program-order / include-graph model

- [x] **Replace the flat "scan every `.tab`/`.inc` file in the workspace" model with an actual `INCLUDE`-graph resolver** ✅ Done (2026-08-26) — `src/includeGraph.ts` (`resolveIncludeGraph(entryFile, readFile, options)`), unit-tested in `test/includeGraph.spec.ts` (19 tests, no live vscode needed — same "pure function + injectable I/O" pattern as `matching.ts`/`fsutils.ts`). Given an entry file and a `(path) => string[] | undefined` reader, it walks `INCLUDE = <file>;` statements (quoted or bare, resolved relative to the *including* file's directory, nesting supported) and tracks `#define`/`#undefine`/`#ifdef`/`#ifndef`/`#else`/`#end` state — including the OR-bracket form `#ifdef [ a b c ]`, AND-via-nesting, and the documented case-sensitivity quirk (`#define`/`#ifdef` names are case-sensitive unless `#ignorecase = yes;` is set, unlike the rest of the case-insensitive language) — to produce one flat, linearly-ordered list of only the *active* source lines across the whole include tree, tagged with their original file+line. `INCLUDE`/`#define`/etc. text inside comments or strings is correctly ignored (reuses `Scope` via a minimal fake `vscode.TextDocument`, exactly like `test/scope.spec.ts`'s `makeDoc()` helper). Include cycles (direct or indirect) and a nesting-depth cap (default 20, mirroring the compiler's documented macro-nesting limit — there's no documented INCLUDE-specific limit) are both detected and reported as structured errors rather than hanging or crashing. On the "wrinkle" flagged when this item was written — appendix error `27: nested INCLUDE not allowed` (line 17220) vs. the main text's explicit "geschachtelte INCLUDEs" support (line 533-534) — nesting is implemented as supported, matching the main text and the multiple real nested-INCLUDE examples elsewhere in the handbook (e.g. `CSVINFILE = csv.csv; INCLUDE = var.inc;` patterns around line 16045-16151); the appendix entry is most likely a legacy or narrower-context restriction (not reproduced here) rather than a current hard rule, but flag this if a real script trips it. **Explicitly out of scope for this pass** (left as plain, unexpanded content — see the module's own doc comment): `#MACRO`/`#DOMACRO` expansion and `#EXPAND` substitution (that's F3's job, built on top of this); and evaluating `#IFEMPTY`/`#IFNEMPTY` (depends on `#EXPAND` values) or `#IFEXIST`/`#IFNEXIST` (depends on variable-definition tracking, itself a *consumer* of this module) — both are conservatively treated as always-active (both branches kept) rather than guessed at, to favor false positives (an extra candidate definition) over false negatives (silently hiding a real one). Not yet wired into `extension.ts`'s providers — that's F3/F4, which now have a correct foundation to build on. `npm test` (60/60), `npm run compile`, `npm run lint` (0 errors) all verified.

## F1 — Core tooling: keyword knowledge base, hover, autocomplete, snippets

- [ ] **Build a mechanically-extracted keyword database from the manuals.** The handbook is largely machine-parseable: many sections use a repeating "Name / Beschreibung" two-column pattern (e.g. the CELLELEMENTS groups around line 10790-10840), and most standalone keywords follow a "Keyword — prose — `Syntax:` — grammar block — example" template. Write an offline extraction script (run once, output committed as a static JSON/TS data file, not re-parsed at runtime) that walks `dokumentation/*.md`, pulls out keyword → {syntax, short description, source file/section} triples, and special-cases: (a) the Name/Beschreibung table blocks, (b) `^Syntax:$`-anchored blocks, (c) PDF-to-markdown artifacts — repeated running headers/footers duplicated mid-section (e.g. spurious "ABSINLABELBOX" headers before unrelated TABLEFORMAT entries around line 13590-13670) that must be filtered out, not treated as real entries. Expect on the order of 600-900 entries once the main handbook and topic manuals (especially the 76KB `GESStabs_OfficeExport.md` and 48KB `GESStabs_GESStabs-Artist.md`, which carry their own large option vocabularies not duplicated in the main handbook) are combined. This database is the shared foundation for the next three items — build it first.

- [ ] **Autocomplete/IntelliSense** (`vscode.CompletionItemProvider`) suggesting: keywords (from the F1 database, with the description as documentation on the completion item), variable/table names already defined earlier in the resolved program order (reuse `Scope`/the symbol providers' matching logic), and macro names with their declared parameter lists. Should respect gessTabs' no-forward-reference rule: don't suggest a variable that's only defined later in the file.
- [ ] **Expand the snippet library well beyond the current single `table` snippet** (`snippets/snippets.json`). Mine the "Syntax:" grammar blocks from the F1 extraction pass to generate skeletons for the highest-traffic statement families: `variable`/`variables`, `recode`, `valuelabels`/`overcode`, `compute` (+ its `add`/`alpha`/`ascend`/... variants), `weightcells`, `#macro`/`#domacro`, `overview`/`xoverview`, `vargroup`/`groups`. Also add a dedicated snippet for the documented `#twobases`-style multi-base-percentaging pattern from `GESStabs_Basiswechsel.md` — the manual presents it as a reusable cookbook macro, which is exactly what a snippet is for.

## F2 — Diagnostics grounded in documented pitfalls

Each item below mirrors a failure mode the manual explicitly calls out (often with its own compiler-level mitigation flag) — these are not speculative lint rules, they're documented "this goes wrong in practice" patterns. Where useful, cross-reference the ~850 numbered compiler error codes in the appendix (`7.3 Liste aller Syntaxfehlermeldungen`, from line 17190) so diagnostic messages read like the real compiler's own errors.

- [ ] **"Empty varlist binds to last-created variable" trap.** Section 3.1 (line ~1240-1267) documents this as the language's own "hoch fehleranfällig" (highly error-prone) mechanism: `RECODE`, `VARTITLE`, `VARTEXT`, and `VALUELABELS` all silently apply to "die zuletzt erzeugte Variable" when no variable list is given — the manual's own worked failure example is `COMPUTE f222 = Q17_1; VARTITLE = "ehemals Q17_1";` silently retitling the *wrong*, pre-existing `f222` instead of a newly-computed one. GESStabs ships `STRICTVARLIST = YES;` purely to outlaw this pattern. Flag empty-varlist usage on these four statements as a warning, with a quick fix (see F5) to insert the actual last-defined variable name explicitly, and a separate one-shot suggestion to add `STRICTVARLIST = YES;` near the top of the entry file.
- [ ] **Unmatched block diagnostics**: `#MACRO`/`#ENDMACRO` and `#IFDEF`/`#IFNDEF`/`#IFEMPTY`/`#IFNEMPTY`/`#IFEXIST`/`#IFNEXIST` (each closed by `#END`, optional `#ELSE`) pairing. Mirrors real compiler errors and is a straightforward bracket-matching pass once the preprocessor tokens are recognized.
- [ ] **Duplicate variable declaration** — mirrors compiler error `8: variable declared twice`.
- [ ] **RECODE bound sanity checks** — `CHECKRECODES = YES;` exists specifically to catch inverted lower/upper bounds; the manual's own detailed RECODE walkthrough (line 6477-6700) is worth re-reading when implementing this, since overlapping ranges are *intentionally legal* (resolved first-match-wins by default, `RECODELASTWINS` to flip it) — don't flag overlap itself, only structurally inverted bounds (lower > upper).
- [ ] **`CARD`/`CARDS` ordering** — mirrors compiler error `25: CARD-value must not be greater than CARDS-value`.
- [ ] **`WEIGHTCELLS` target percentages summing to 100%** per variable (`GESStabs_Gewichten.md`) — a cheap, purely-arithmetic static check on the statement's own operands, no data access needed.
- [ ] **Mutually-exclusive table/cell-option diagnostics**: `HARMONICMEAN`/`GEOMETRICMEAN` combined with other cell contents; `MEDIAN` combined with anything beyond frequencies/percentiles; `CELLSET`'s fixed allow-list of element types (line ~11453-11460); `COLUMNPERCENT100` used with multi-response variables/OVERCODEs/suppressed-MISSING tables (flagged "Achtung: nicht geeignet" twice in the handbook, line 10834 and 10875); `INVERTOUT` + `UPDATEINVERT` in the same pass (`GESStabs_InvertierteDateien.md:195`, "nicht erlaubt"). Same recurring pattern across topic manuals — implement as a small table of `{optionA, optionB, message}` rules rather than bespoke code per pair.
- [ ] **`#define`/`#ifdef`/macro-name case-sensitivity gotcha.** Unlike the rest of the (case-insensitive) language, preprocessor names are case-sensitive by default (`#define xyz` then `#ifdef XYZ` is false) unless `#IGNORECASE = YES;` is set — flag an `#ifdef`/`#ifndef` reference whose name doesn't exactly match any `#define` in scope but *does* match case-insensitively, since that's almost certainly the bug rather than an intentionally-undefined flag.

## F3 — Macro tooling ✅ Done (2026-08-26)

The manual concedes macro debugging is hard enough to need its own compiler feature (`MACROPROTOCOL = <file> [DOMACRO];`, justified at line 855-858: "man sieht im Quelltext nur die Macroanweisungen, aber nicht das expandierte Produkt" — you only see the macro calls in source, not the expanded result). These items bring an equivalent capability into the editor.

All four items are built on a new pure, unit-tested engine, `src/macroExpansion.ts` (`findMacroDefinitions`, `findMacroCalls`, `expandMacro`, `findParamReferenceAt`; 19 tests in `test/macroExpansion.spec.ts`, several taken directly from the handbook's own `#example`/`#mitOC`/`#typ_a` worked examples), plus a thin vscode-wiring layer, `src/macroProviders.ts`. Macro names are matched case-insensitively, consistent with `regex.ts`'s existing `macroDefRe` and the language's general case-insensitivity (unlike `#define`/`#ifdef` names, which F0 already established are case-sensitive).

- [x] **"Show expanded macro" hover** on a `#name(...)` call site ✅ — `GesstabsMacroHoverProvider`. Parameters are substituted by literal substring match (not word-boundary), so `&varname` immediately followed by a literal suffix (`&varname_OC`) expands correctly, matching the handbook's own `#mitOC` example exactly. Nested calls to other *known* macros within the body expand transitively (depth-capped at 20, mirroring the compiler's documented macro-nesting limit), matching real compiler behavior.
- [x] **`&paramname` go-to-definition inside a macro body** ✅ — wired into the existing `GesstabsDefintionProvider` (checked before the normal word-based lookup) rather than a separate provider, since go-to-definition is a single vscode contribution point per language. Uses the same substring/prefix-matching logic as expansion (`&varname_OC` resolves to the `varname` parameter) so hovering/jumping from a suffixed reference works the same way expansion does. (A dedicated hover *for* param references, beyond go-to-definition, wasn't added — judged lower value than the other three items given time spent.)
- [x] **Signature help while typing a macro call** ✅ — `GesstabsMacroSignatureHelpProvider`, triggered on `(` and ` `, showing the declared `&param` list from the matching `#MACRO` definition with a best-effort active-parameter guess (counts whitespace-separated tokens typed so far). Only plain `#MACRO`/direct calls are covered, not `#DOMACRO`/`#DOMACRO2` (see scope note below).
- [x] **CodeLens on `#MACRO` declarations showing a usage count** ✅ — `GesstabsMacroCodeLensProvider`, counting `#name(...)` call sites across the *resolved* workspace (via `symbolIndex`/F0's include graph), so counts reflect files actually `INCLUDE`d and active `#ifdef` branches, not just any `.tab`/`.inc` file sitting on disk.
- **Explicitly out of scope, documented as known limitations in `src/macroExpansion.ts`'s own header comment**: (1) `#DOMACRO`/`#DOMACRO2`/`#DOMACRO3`/`#DOMACRO4` looping expansion (repeats a call over a range/list/CSV file) — only plain `#name(args)` direct calls are recognized; (2) the handbook's `#call(&index &namepart &macroname)` → `#&macroname(&namepart&index)` pattern, where the callee name is itself a parameter and so never appears literally at the call site — such calls are simply not recognized as calls to a *known* macro, exactly as originally scoped out below.
- Refactor side-effect: extracted `fixDriveCasingInWindows`/`getWorkspaceFolderPath`/`normalizePath`/`makeWorkspaceReader`/`resolvedLineRange`/`findWorkspaceFiles` out of `extension.ts` into a new shared `src/workspaceFiles.ts`, since both `extension.ts`'s providers (F4) and the new macro providers need them — avoids the alternative of duplicating them into `macroProviders.ts`, and is a small, organic first step in the direction of the still-open P3 "split `extension.ts` into `src/providers/*.ts`" idea, without attempting that larger refactor now.
- **Corrections from live debugging with a gessTabs developer, after initial rollout** (2026-08-27): (1) a macro call must start in column 1 of a line (leading whitespace allowed) — any other `#name` occurrence, anywhere, is an `#EXPAND` reference, never a macro call; `findMacroCalls` is now anchored accordingly (`^\s*#name\s*\(`) and returns at most one call per line, instead of scanning the whole line for any `#name(` shape. (2) Macro call/param tokens are plain tokens — quoting is purely a grouping device for a token containing whitespace (`#f( Kinder weiblich 2 )` vs. `#f( "keine kinder" kinder "(1 eq 1)" )`); the quote characters themselves are never part of the substituted value, so `parseTokenList` now strips them (while still keeping a deliberately-empty `""` argument as a real, position-preserving empty token) — the hover's "Expanded `...`:" header now shows the original call verbatim (`call.raw`, quotes and all) while the expanded body below uses the quote-stripped values, matching real compiler behavior. (3) Added `#EXPAND` hover: `findExpandDefinitions` parses `#EXPAND #name value` lines (name matched case-sensitively, like `#define`/`#ifdef` — unlike macro names) into a name→value map; hovering a bare `#name` that isn't a column-1 macro call now shows the defined value via the same `GesstabsMacroHoverProvider`. Also found and fixed the actual root cause of the original `#scorecard`-not-found report along the way: `resolveIncludeGraph` only checked whether a line's *first* character was inside a comment (to decide whether to skip it entirely), not whether a comment appeared *partway* through an otherwise-real line — a `{ }`-commented-out old macro version with an unbalanced `#MACRO`/`#ENDMACRO` count (real code, verified by hand, compiling cleanly with the actual gessTabs compiler) was tripping `findMacroDefinitions`'s line-scanning regexes, which aren't anchored to line-start the way the directive regexes are. Comment characters are now blanked to spaces (preserving offsets) before any downstream consumer sees the line. `npm run compile`, `npm run lint` (0 errors — added a `max-classes-per-file: 3` override for `macroProviders.ts`), `npm test` (111/111) all verified.

### F3 follow-ups (not yet done)

- [ ] **Suppress hover inside comments.** `GesstabsMacroHoverProvider` currently runs `callAtPosition`/`findHashNameAt` directly against the *raw* current line text (`document.lineAt(position.line).text`) with no comment/string-scope check at the cursor position itself — unlike `resolveIncludeGraph`'s resolved workspace index (fixed above), which now blanks comment text before `findMacroDefinitions`/`findMacroCalls` ever see it. ## F4 — Fix and complete the existing go-to/references providers ✅ Done (2026-08-26)

- [x] **Re-implement `GesstabsReferenceProvider.provideReferences`** ✅ — no longer disabled. Built on a new shared module, `src/symbolIndex.ts` (`buildWorkspaceIndex`/`findDefinitionLine`/`findAllUsages`/`findWordRangeInLine`, unit-tested in `test/symbolIndex.spec.ts`, 13 tests), which sits directly on top of F0: it determines which discovered `.tab`/`.inc` files are actual entry points (a file never reached by any other file's `INCLUDE`), resolves each root's include graph, and merges them into one combined, program-ordered view. `findDefinitionLine` scans *backward* from the cursor's resolved position (respecting the no-forward-reference rule); `findAllUsages` returns every matching line across the merged view. `GesstabsDefintionProvider.provideDefinition` was rewritten on the same foundation too (not just references) — it no longer does an unordered per-file scan ignorant of `#ifdef` branches, which was exactly the correctness gap F0 itself was written to close, so leaving it on the old approach while only fixing references would have been inconsistent. Both providers are also now plain `async` methods instead of manual `new Promise(...)` executors, and no longer need `vscode.workspace.openTextDocument` per candidate file at all — `symbolIndex` reads plain file content (the current document's own live editor buffer for itself, so a user's own unsaved edits are always visible; `fs.readFileSync` — last-saved disk state — for every other file, matching what the real compiler would see if it ran right now). One correctness fix along the way: `vscode.Uri.fsPath`'s drive-letter casing isn't guaranteed to match the `fixDriveCasingInWindows()`-normalized paths `getAllFilenamesInDirectory` produces (the exact inconsistency that function exists to work around) — added a `normalizePath()` helper and applied it everywhere a document path is compared against or looked up in the index, otherwise the current-file/live-buffer detection could silently miss on Windows.
